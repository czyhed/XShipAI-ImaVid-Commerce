# 数字人持物口播方案 vs 当前项目：对齐与差距分析

日期：2026-11-18  
对照文档：《数字人持物口播-技术方案》v1.1（5~10 秒短视频）  
当前实现：`docs/requirements/presenter-video-grilling.md`（H3 参考模式人物口播，5~8 秒）

## 0. 一句话结论

这份方案**不是当前人物口播功能的小改**，而是一条不同的生成链路：

- 当前：人物图 + 商品图 → **H3 参考模式一次生成**（台词作为参考音频 / 后期混音）。
- 方案：持物图 → **图生视频底片** → TTS → **只改嘴的对口型** → 标识转码。

当前已有的 TTS、素材库、运行队列、ffmpeg、模型中心可以复用；但**持物图、独立底片、独立对口型、质量门禁、AI 标识、人工确认状态**目前都没有做。方案里的“手和商品在静态图里就位，全程只驱动嘴部”是当前 H3 链路无法保证的。

## 1. 对齐总表

| 方案要求 | 当前实现 | 结论 |
| --- | --- | --- |
| 5~10 秒单段直出 | 人物口播 UI 为 5~8 秒；H3 本身支持 4~30 秒 | **需改**：扩展时长选项与文案上限 |
| 9:16、1080×1920 | 默认 9:16，但默认 768P；1080P 可选 | **需改**：该功能默认 1080P / 9:16 |
| 人物来源：真人照片 / 已有形象 | 上传真人照片、AI 生成定妆照、从已生成数字人中选择 | **部分具备**；没有独立“形象”实体与音色样本 |
| 商品图 1 张即可 | 支持 1~3 张商品参考图 | **基本兼容** |
| 持物图：人物手持商品，人工确认 | 只生成人物定妆照；商品图作为 H3 参考，不在静态图里合成 | **完全没做** |
| 图生视频底片：固定机位、手和商品静止 | 没有独立底片阶段；H3 参考模式直接生成带人物、商品、台词的视频 | **完全没做** |
| TTS：火山引擎 | 已接入火山 TTS，逐句合成、拼接、字幕时间戳 | **可直接复用** |
| 对口型：只替换嘴部 | H3 把 TTS 音频作为参考音频，整幅画面重绘 | **核心差距**：不是“只改嘴” |
| AI 标识 + 隐式元数据 | 只有 H3 可选的 `aigc_watermark` 开关，成片不强制加标识 | **需新增** |
| 主选 Seedream / 可灵 | 图片走 OpenAI-compatible / OMYAI；视频只有 MiniMax H3 | **需新增 Provider** |
| Provider 适配器契约（submit/query/estimateCost） | 现有 `model-hub` 按 kind 分派，图片/视频各自函数；无统一 `estimateCost` | **需改造** |
| 任务状态机含 `waiting_human`、stage、progress | 运行状态只有 queued/submitting/running/succeeded/failed/cancelled | **需新增** |
| 质量门禁：人脸、手部 IoU、商品 SSIM、口型 | 没有自动质量门禁 | **完全没做** |
| 成本预估接口 | 只有 H3 积分预估；没有分阶段成本 | **需新增** |
| 合规：授权留痕、广告审核、7 日删除 | 有素材回收站/删除，但没有真人授权、广告审核、7 日自动清理 | **需新增** |
| `/v1/...` 公开 API | 现有 `/api/creation/projects/:id/...` | **需决策**：新建外部 API 还是映射到现有 API |

## 2. 当前已经具备、可直接复用的部分

1. **图片生成 / 改图**
   - `server/providers/creation-image.mjs` 已支持多张参考图 + 蒙版。
   - OMYAI 已实测两张参考图合成；这意味着“人物 + 商品 → 持物图”在 v0.1 可以先复用现有图片编辑，不必等 Seedream 适配器。

2. **视频生成与轮询**
   - `server/providers/creation-video.mjs` 已支持 H3 的文生、首尾帧、参考模式，4~30 秒，480P~4K，9:16，提交/查询/取消/下载。
   - `server/creation-projects.mjs` 的 `preview → start → insertRun → drive` 已有冻结输入、幂等请求编号、轮询、取消、失败重试。

3. **TTS 与音频处理**
   - `server/providers/volc-tts.mjs` + `server/creation-voice.mjs`：逐句合成、拼接、字幕时间戳、后期混音、去音轨。
   - `server/audio-join.mjs` 已有 ffmpeg 的 join / mix / strip，可直接用于时长对齐和配音。

4. **成片与素材**
   - `server/video-compile.mjs` 已做 H.264 拼接、可选字幕烧录。
   - MinIO 私有素材、资产库、项目导出、分镜表、结果素材归集都已具备。

5. **模型中心与权限**
   - 动态渠道、AES-GCM 加密 Key、模型能力勾选、默认环节、CSRF/If-Match、角色权限都已具备。
   - 已有协议：`openai-compatible`、`anthropic`、`minimax-h3`、`volcengine-tts`。

6. **人物口播 UI 外壳**
   - `web/src/components/PresenterWizard.jsx` 已有人物上传、AI 定妆、商品选择、台词、时长、展示方式、配音方式、积分预估。
   - 这些可以保留，改造成“持物图确认 + 5~10 秒 + 新配音方式”。

## 3. 需要改造的部分

### 3.1 参数与 UI

- `shared/creation-presenter.mjs`
  - `PRESENTER_DURATIONS` 从 `[5,6,7,8]` 改为 5~10 秒（或 5/10 两档，见待确认）。
  - `presenterDialogueLimit` 从“时长 × 4”调整为方案里的 5 秒 20~30 字、8 秒 32~45 字、10 秒 40~60 字；至少要加下限/上限提示。
  - 默认分辨率从 768P 改为 1080P（或该功能单独默认 1080P）。
- `web/src/components/PresenterWizard.jsx`
  - 时长选项、字数提示、默认分辨率同步调整。
  - 增加“持物图确认”步骤：候选图、放大检查手/商品、确认/重生成。
  - 增加“AI 标识不可关闭”的说明和授权勾选。

### 3.2 人物口播创建逻辑

- `server/creation-projects.mjs` 的 `createPresenter`
  - 当前只创建：人物参考节点 + 商品参考节点 + 视频节点。
  - 需要改为：人物图 + 商品图 → **持物图编辑节点** → 视频节点；视频节点引用持物图，而不是把商品图继续传给视频模型。
  - 视频提示词不再要求“商品参考图”，而是“以持物图为首帧，保持手和商品静止，只做呼吸/眨眼/轻微头部动作”。

- `presenterImage`
  - 当前只生成人物定妆照。
  - 需要新增“持物图”生成：输入人物图 + 商品图，输出 2~4 张候选；失败时提示品类暂不支持。

### 3.3 运行编排

当前一次运行 = 一次供应商调用。方案要求一次任务内串行/并行四段：

```text
持物图 → 底片(5~10s) ─┐
        → TTS        ─┴→ 对口型 → 标识转码
```

需要新增一层“任务编排”，可选两种做法：

1. **新增 `sj_presenter_jobs`**：一个 job 下挂多个 stage run，单独记录 stage/progress/waiting_human；画布仍只看到一个视频节点。
2. **扩展现有 `sj_creation_runs`**：增加 `parent_run_id`、`stage`、`progress`，由 `drive` 按 stage 推进。

无论哪种，都要处理：
- 持物图完成后暂停，等待人工确认；
- 底片与 TTS 并行；
- 对口型失败重试/换供应商；
- 整单 15 分钟超时；
- 前端显示当前处于哪一段。

### 3.4 Provider 适配器

- 需要新增可灵（Kling）：
  - 图生视频（5s/10s）；
  - 对口型；
  - 可灵使用 AccessKey + SecretKey 生成 JWT，当前 `sj_model_channels` 只有单个 Key 字段，需要扩展密钥结构或增加签名配置。
- 可选新增 Seedream：
  - 如果现有 OpenAI-compatible 图片编辑能满足持物图质量，v0.1 可以先不接 Seedream；质量不够再替换。
- `server/channels.mjs` 的协议白名单、`server/model-hub.mjs` 的分派、模型中心 UI 都要同步增加。
- 现有“视频执行器仅支持 MiniMax H3”的限制要放开，并区分 `image-to-video` / `lipsync` 能力。

### 3.5 TTS 时长对齐

- 方案要求底片与音频偏差 ≤0.3 秒。
- 当前 `dubSuggestion` 只提示“配音超过分镜时长”，`mix` 用 `-shortest` 截断。
- 需要新增：
  - 首尾静音裁剪；
  - 超长时自动微调语速（±15% 以内）或提示压缩文案；
  - 不足时补静音/补帧；
  - 对口型前校验音频与底片时长。

### 3.6 成片标识与转码

- `server/video-compile.mjs` 目前只做拼接和可选字幕，没有 AI 标识。
- 需要新增 `finalize`：
  - 右下角“AI 生成”角标（建议用 PNG overlay，避免服务器缺少 drawtext 字体）；
  - `-metadata comment="AI-generated content; ..."`；
  - H.264 / yuv420p / 25fps / CRF 18；
  - 标识不可由用户关闭。
- H3 的 `aigc_watermark` 只能作为供应商侧附加，不应作为唯一合规手段。

### 3.7 成本与计费

- 当前只有 H3 积分预估，且积分单价在渠道 `executorConfig.pointPrices`。
- 方案要求 `/pricing/estimate`，按持物图、I2V、TTS、对口型分别计价。
- 需要决定：
  - 继续用积分，还是按人民币成本展示；
  - 各阶段单价配置在哪；
  - 失败重试是否计入用户成本。

## 4. 目前完全没有做的部分

1. **持物图合成**：人物 + 商品 → 手持商品的静态图，含候选、人工确认、手指数/穿模检查。
2. **独立图生视频底片**：固定机位、无镜头运动、手和商品静止的 5~10 秒底片。
3. **只改嘴的对口型**：当前 H3 是整幅重绘，不是嘴部替换。
4. **质量门禁**：人脸检测、手部框 IoU、商品区域 SSIM、口型主观评分。
5. **任务状态机**：`waiting_human`、`stage`、`progress`、`retrying`、整单 15 分钟超时。
6. **自动重试/主备切换**：当前平台明确“不自动重提、不自动换模型、不付费重试”；方案要求重试 2 次并切换备选供应商，两者冲突。
7. **AI 标识与隐式元数据**：当前没有强制成片标识。
8. **授权留痕**：真人照片/音色的授权勾选、`user_id + 素材指纹 + 时间 + IP`、保存 ≥3 年。
9. **广告内容审核**：功效、绝对化用语的拦截钩子。
10. **7 日数据清理**：当前只有回收站/永久删除，没有自动保留期。
11. **20 个 SKU 验收**：没有真实商品通过率、口型评分、耗时、成本数据。
12. **外部 `/v1` API**：当前只有 `/api/creation/...`，没有方案里的 avatar / compose / confirm / projects / pricing 接口。

## 5. 与当前平台规则冲突、需要先拍板的点

### 5.1 自动重试 / 主备切换

方案 §4/§8 要求“失败自动重试 2 次，仍不达标换供应商”。  
当前 `AGENTS.md` / ADR 明确：**不自动重提、不换模型、不付费重试**，失败后由用户确认重试。

这不是技术难度，是**产品/费用策略冲突**。如果按方案做，必须修改现行规则，并明确重试费用由谁承担。

### 5.2 时长档位

方案内部不一致：
- §0 / §1 写 5~10 秒；
- §4 写“5s 或 10s”；
- §2.5 又给了 8 秒字数；
- 当前实现是 5~8 秒。

需要确认是 **5/10 两档**，还是 **5~10 任意整数秒**。这会直接影响 UI、文案上限、底片生成和成本。

### 5.3 HeyGen 路线

上一轮沟通的方向是 HeyGen Talking Photo；这份方案明确排除 HeyGen（大陆不可直连、仅国际卡、数据存美国、无中国备案），主选可灵 + Seedream + 火山。

如果按这份文档执行，**HeyGen 不接入**。这是一个路线切换，需要确认以文档为准。

### 5.4 质量门禁与“无 GPU”

方案要求手部 IoU、商品 SSIM、人脸检测。  
当前没有 CV 推理服务。可以用 CPU + OpenCV/ffmpeg 做部分检查，但手部关键点/检测通常需要模型；这与“第一阶段不碰 GPU”不冲突，但需要额外的 CPU 服务或第三方审核 API。

v0.1 建议：**持物图人工确认 + 底片首末帧人工抽查**，自动门禁后置；否则工期会被 CV 服务拖长。

### 5.5 API 形态

方案的 `/v1/avatars`、`/v1/avatar-products/compose` 等是独立服务 API。  
当前平台是项目制 `/api/creation/projects/:id/...`。需要确认：
- 是在现有项目里加内部编排（推荐，复用权限/素材/运行记录）；
- 还是另做一套 `/v1` 对外 API（需要额外的鉴权、限流、版本、Webhook）。

### 5.6 成本口径

方案按人民币 ¥2~6/条估算；当前平台按 H3 积分记录用量，不承诺货币成本。  
需要确认是继续积分，还是给数字人功能单独做人民币报价。

## 6. 建议的落地路径

### 方案 A：只改提示词（不推荐，已接近当前实现）

继续用 H3 参考模式，只改 prompt。  
**不能解决**手/商品漂移和“只改嘴”的问题；方案的核心质量目标达不到。

### 方案 B：v0.1 验证版（推荐先做）

```text
人物图 + 商品图
→ 现有图片编辑合成持物图（2~4 张候选，人工确认）
→ H3 首帧图生视频 5s 底片（固定机位 prompt）
→ 火山 TTS
→ 可灵对口型
→ ffmpeg 加 AI 标识/转码
```

特点：
- 复用现有图片编辑、H3、火山 TTS、素材库、运行队列；
- 只新增 **可灵对口型** 一个 Provider（如果 H3 底片能被可灵接受）；
- 新增一个轻量编排层和持物图确认 UI；
- 先验证“手和商品是否稳定”，再决定是否接 Seedream / 可灵 I2V。

风险：
- 可灵对口型是否接受第三方底片，需要先用 1 条样片验证；
- H3 底片仍可能移动手/商品，需要 prompt + 人工抽查；
- 可灵鉴权是 AccessKey/SecretKey，需要扩展渠道密钥结构。

### 方案 C：完全按文档（v1）

```text
Seedream 持物图 → 可灵 I2V 底片 → 火山 TTS → 可灵对口型 → ffmpeg 标识
```

特点：
- 最接近文档的质量目标；
- 需要新增 Seedream + 可灵两个 Provider，扩展模型中心、密钥、能力、计费；
- 需要完整质量门禁与任务状态机；
- 工期明显大于方案 B。

### 建议

1. **先做 P0 可行性验证，不写平台代码**：5 件商品、1 张人物图，手工/脚本走一遍“持物图 → H3 或可灵底片 → TTS → 可灵对口型”，逐帧看手指、商品、口型。
2. 如果 5 件中 ≥4 件手部无明显形变，再按方案 B 做平台化。
3. 如果 H3 底片不满足，再升级到方案 C 的可灵 I2V。
4. 不要在 P0 之前接 Seedream/可灵全套，也不要在当前 H3 链路上继续加提示词。

## 7. 需要确认的问题

1. 时长是 **5/10 两档**，还是 **5~10 任意整数秒**？
2. 是否确认放弃 HeyGen，改走文档里的境内 API（可灵 + Seedream + 火山）？
3. 自动重试/主备切换是否要改现行“不自动重提、不换模型”的规则？
4. v0.1 是否接受“持物图人工确认 + 底片人工抽查”，自动质量门禁后置？
5. 数字人功能是集成进现有项目画布，还是另做 `/v1` 外部服务？
6. 成本继续用积分，还是单独做人民币报价？
7. AI 标识是否强制、不可关闭？真人照片/音色是否强制授权勾选？
8. 是否先用现有图片编辑合成持物图，还是必须接 Seedream？

## 8. 结论

- **能复用**：TTS、素材库、运行队列、ffmpeg、模型中心、人物口播 UI 外壳。
- **必须新做**：持物图合成与确认、独立底片、只改嘴的对口型、任务编排、质量门禁、AI 标识、授权留痕。
- **最大风险**：当前 H3 链路与方案的核心原则相反；不改链路，只改提示词，达不到“手和商品全程稳定”的目标。
- **建议**：先用 5 件商品做 P0 样片验证，再决定方案 B（轻量）还是方案 C（完整）。

## 9. 已确认决策（2026-11-18）

| 项 | 决定 | 影响 |
| --- | --- | --- |
| 时长 | **v0.1 固定 8 秒** | 文档的 5/10 两档不再采用；8 秒按 32~40 字控制，TTS 与底片按 8 秒 ±0.3 秒对齐 |
| 路线 | **放弃 HeyGen，走境内 API** | 不再接 HeyGen；主链路使用境内图片编辑 + 境内视频/对口型 + 火山 TTS |
| 重试 | **免费查询自动重试；提交仅在确定未受理时自动重试；付费生成默认人工确认，可选自动重试预算** | 不采用文档的“无条件自动重试 2 次 / 自动换供应商” |
| 平台形态 | **先做方案 B，P0 不写平台代码** | P0 验证通过后再平台化；方案 C 仅在 B 不达标时启动 |

补充：如果“境内 API”是硬约束，方案 B 里的“现有图片编辑”不能直接假定为当前 OMYAI 渠道；需确认 OMYAI 的境内合规性，必要时改用即梦 Seedream、通义万相或火山方舟的图片编辑通道。
